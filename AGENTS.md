# Инструкции для coding agent

Перед изменением кода обязательно прочитай все спецификации в каталоге `spec/`:

- `spec/SPEC.md` — функциональные требования, API, права доступа, тесты и Definition of Done;
- `spec/ARCHITECTURE.md` — разделение моделей, доменной логики, selectors и API endpoints;
- `spec/LOCAL_DEVELOPMENT.md` — Docker Compose, demo users/tasks и локальный API E2E-сценарий;
- `spec/FRONTEND.md` — адаптивный UI, системная/светлая/тёмная темы и браузерные smoke-checks;
- `spec/DOCUMENTATION.md` — требования к подробному README, дополнительной документации и проверке инструкций.

Эти документы — основной источник требований. Все спецификации, кроме этого файла `AGENTS.md`, должны храниться в `/spec/`; не создавай дубликат `SPEC.md` в корне репозитория.

## Рабочий процесс

- Сначала изучи текущее состояние репозитория: существующие файлы, инструкции, конфигурацию, `git status` и доступные команды тестирования.
- Сохраняй существующую рабочую реализацию и стиль проекта; не пересоздавай проект с нуля, если в репозитории уже есть полезный код.
- В начале сообщи короткий план и найденные риски, затем продолжай реализацию небольшими логическими шагами; не останавливайся на одном только плане.
- Не задавай вопросы о решениях, уже закреплённых в спецификациях. При отсутствии несущественной детали выбери простое и безопасное решение и задокументируй его.
- Разделяй persistence-модели, доменные services, selectors, REST API и HTML presentation слой по `spec/ARCHITECTURE.md`. Не помещай бизнес-правила целиком в views или serializers.
- Реализуй browser UI по `spec/FRONTEND.md`; не делай отдельный frontend-сервис и не добавляй тяжёлый frontend framework без необходимости.
- Напиши подробный, точный README и придерживайся `spec/DOCUMENTATION.md`, особенно для тестирования через Docker Compose.
- После каждого существенного этапа запускай релевантные тесты. В конце запусти весь набор тестов, линтер, проверки миграций и доступные проверки Docker Compose.
- Проверь стартовый сценарий `docker compose up --build`, повторный запуск (без дублирования demo data), сценарий сброса volume и фактические команды E2E из README.
- Проведи UI smoke-check на desktop и узком мобильном viewport: вход, список/создание/обновление задачи, назначение, завершение, комментарии и все три режима темы. Не заявляй о браузерной проверке, если её не выполнял.
- Сверь README с реальными файлами, адресами, командами и демо-данными; убери TODO и заполнители.
- Не ослабляй тесты, проверки доступа или валидацию только ради успешного завершения.
- Не добавляй ненужные зависимости, отдельные frontend-сервисы или дополнительные инфраструктурные компоненты сверх того, что требуется в спецификациях.
- Не коммить секреты, `.env`, локальную базу данных, токены, временные артефакты и файлы окружения.
- Не заявляй об успешных проверках, которые фактически не запускал.

## Завершение работы

В финальном сообщении перечисли реализованные возможности, ключевые файлы/решения, команды проверок и фактические результаты. Укажи известные ограничения и проверки, которые не удалось выполнить. Сверь результат с чек-листом Definition of Done в `spec/SPEC.md`.
