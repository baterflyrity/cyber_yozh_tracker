# Спецификация веб-интерфейса и адаптивного дизайна

Этот документ дополняет `spec/SPEC.md`. Веб-интерфейс обязателен: задача должна быть пригодна для демонстрации в браузере, а не только через Swagger UI. При этом задача остаётся backend-oriented: не создавайте отдельное frontend-приложение и не добавляйте тяжёлый JS-фреймворк.

## 1. Технологии и границы

- Использовать Django templates для HTML-оболочки и vanilla JavaScript для взаимодействия с REST API через `fetch`.
- CSS и JS хранить в Django static files и отдавать тем же приложением. Не требуются Node.js, npm, отдельный dev server или отдельный контейнер frontend.
- UI должен использовать существующие API endpoints. Не дублировать бизнес-правила, доступ к данным или запись в БД внутри HTML page views.
- Рекомендуемые маршруты: `/` — рабочая область задач, `/login/` — вход, `/register/` — регистрация. Допускается иная структура, если все пути стабильны и понятно документированы в README.
- Swagger UI, Redoc и OpenAPI должны продолжать работать по путям из `spec/SPEC.md`.

## 2. Обязательные пользовательские сценарии

Через UI пользователь должен уметь:

1. Зарегистрировать аккаунт и войти в систему.
2. Выйти из текущей сессии.
3. Просматривать доступные ему задачи в списке.
4. Искать задачи по заголовку/описанию и фильтровать их как минимум по статусу «выполнена / не выполнена».
5. Создать задачу с заголовком и описанием.
6. Открыть задачу и просмотреть её описание, создателя, исполнителя, статус, даты и комментарии.
7. Как создатель задачи — изменить заголовок/описание, назначить активного пользователя или снять назначение, изменить статус и удалить задачу.
8. Как исполнитель — изменить только статус выполнения. Интерфейс может скрывать недоступные действия, но API обязан независимо проверять каждую операцию.
9. Добавить комментарий к доступной задаче; изменять и удалять комментарии только в пределах серверных прав.
10. Переключить тему оформления между «Системная», «Светлая» и «Тёмная».

Не нужно создавать отдельные экраны администратора, real-time обновление, уведомления, drag-and-drop, сложную аналитику, вложения или другие возможности, которых нет в основном задании.

## 3. Структура интерфейса

Предпочтительна лаконичная рабочая панель с визуальной иерархией, а не набор неоформленных HTML-форм.

- **Общая шапка:** название/знак приложения, контекст страницы, селектор темы, имя пользователя и действие выхода после авторизации.
- **Список задач:** заголовок раздела, кнопка создания, поле поиска, фильтр статуса, понятные индикаторы статуса и назначенного пользователя.
- **Карточка/строка задачи:** название, короткий фрагмент описания (если есть), статус, автор/исполнитель и дата последнего изменения. Длинные значения не должны ломать сетку.
- **Форма задачи:** заголовок, описание, выбор исполнителя из справочника активных пользователей, кнопки сохранить/отмена. Серверные валидационные ошибки должны показываться рядом с соответствующими полями или в доступном сообщении.
- **Детали задачи:** все основные поля, разрешённые действия, история комментариев и форма нового комментария.
- **Подтверждение удаления:** использовать понятный диалог подтверждения, чтобы исключить случайное удаление.
- **Пустое состояние:** объяснение, почему список пуст, и полезное действие, если пользователю разрешено создать задачу.
- **Состояния загрузки и ошибок:** показывать визуальную обратную связь во время запросов, ошибки API и возможность безопасно повторить действие; не оставлять экран в бесконечном состоянии загрузки.

Не обязательно соблюдать буквальную структуру этих компонентов: важны доступность всех обязательных сценариев, единый визуальный язык и отсутствие дублирования логики.

## 4. Визуальные требования

- Современный, аккуратный, сдержанный интерфейс с хорошей типографикой, ясной иерархией, равномерными отступами, согласованной системой радиусов, границ, теней и состояний элементов.
- Использовать небольшую согласованную палитру с отдельными токенами для фона, поверхности, основного/вторичного текста, границ, акцента, успеха и ошибки. Не задавать все цвета напрямую в разрозненных селекторах: использовать CSS custom properties.
- Статусы задач различаются не только цветом, но и текстом/иконкой/меткой.
- Предпочитать нативные, доступные HTML controls или простые кастомные controls с полноценной клавиатурной поддержкой. Не делать действия доступными только при наведении мыши.
- Анимации короткие и ненавязчивые. Учитывать `prefers-reduced-motion: reduce` и отключать/уменьшать необязательное движение.
- Не использовать удалённые CDN как обязательную зависимость интерфейса. Приложение должно корректно отображаться без внешних шрифтов, скриптов или изображений.
- Не оставлять emoji единственным обозначением кнопки или статуса; у icon-only controls должен быть доступный текст/`aria-label`.

## 5. Адаптивность

Интерфейс должен оставаться полноценным на мобильных устройствах, планшетах и desktop. Реализуйте fluid layout и разумные breakpoints, не привязываясь к одному конкретному разрешению.

Минимум проверить viewport шириной около 320–375 px (узкий смартфон), 768 px (планшет) и 1280–1440 px (desktop):

- нет горизонтальной прокрутки всей страницы;
- формы и кнопки не обрезаны и не требуют недоступного hover;
- длинные заголовки, описания и usernames переносятся/обрезаются разумно;
- списки задач превращаются в удобные компактные карточки или адаптивную таблицу;
- диалог/форма задачи пригодны для использования на мобильном экране;
- основные действия остаются видимыми и доступны пальцем/клавиатурой;
- меню/фильтры на маленьком экране не перекрывают содержимое без возможности закрытия.

Не требуется pixel-perfect соответствие существующему продукту или макету. Главные критерии — цельность, читаемость, функциональность и отсутствие поломок на малом экране.

## 6. Системная, светлая и тёмная темы

Селектор темы должен иметь ровно три понятных режима: **Системная**, **Светлая**, **Тёмная**.

- **Системная:** определяет текущую схему по `prefers-color-scheme` и реагирует на изменение системных настроек во время открытой страницы.
- **Светлая:** принудительно включает светлую палитру независимо от настройки ОС.
- **Тёмная:** принудительно включает тёмную палитру независимо от настройки ОС.
- Выбор пользователя сохраняется между перезагрузками страницы (предпочтительно в `localStorage`). Если пользователь ещё не делал выбор, по умолчанию используется системная тема.
- Не допускать заметной вспышки противоположной темы при первоначальной загрузке: применять сохранённый режим до основного отображения страницы, насколько это разумно для Django templates.
- Менять всю систему токенов, включая фон страницы, поверхности, текст, поля ввода, меню, диалоги, границы и статусные цвета. Тёмная тема не должна сводиться к инверсии только основного фона.
- Проверить читаемый контраст в обеих темах, видимость focus/disabled/hover состояний и корректность сообщений об ошибках.

Предпочтение темы — настройка отображения, не доменные данные пользователя; не требуется хранить её на сервере.

## 7. Аутентификация UI и безопасная работа с API

- UI использует API для входа, регистрации и задач; токены не должны появляться в URL, HTML, сообщениях об ошибках или логах.
- Для минимизации срока жизни клиентских токенов хранить JWT только в `sessionStorage` или в памяти текущей вкладки, не в `localStorage`. При истечении access token выполнить максимум одну попытку обновления через refresh endpoint и повторить первоначальный запрос не более одного раза; при неудаче очистить состояние авторизации и вернуть пользователя на вход.
- Все запросы должны корректно обрабатывать сетевые ошибки, HTTP 401/403/404/400 и истечение сессии. Не показывать stack traces пользователю.
- Безопасно вставлять пользовательские строки в DOM. Не использовать `innerHTML` для заголовков, описаний или комментариев от пользователя без надёжного экранирования; предпочтительны `textContent` и создание DOM-узлов.
- Не хранить пароли; очищать поля пароля после успешного входа/регистрации.
- Запреты и авторизация всегда enforced сервером. Сокрытие кнопки в браузере — лишь UX, не механизм безопасности.

## 8. Доступность

- Использовать семантические landmark-элементы и понятную структуру heading.
- Каждый input/select/textarea должен иметь связанный label; ошибки валидации должны программно связываться с полем и объявляться доступным способом при необходимости.
- Все действия доступны с клавиатуры; порядок tab логичен, focus заметен и не должен теряться после закрытия диалога или ошибки.
- Диалоги должны иметь имя, управление фокусом и закрытие клавишей Escape, если это реализовано как modal.
- Цвет не должен быть единственным способом различать статус или ошибку. Учитывать `prefers-reduced-motion`.

## 9. UI smoke-check перед завершением

В README добавить короткий чек-лист ручной проверки UI и фактически пройти его, если доступна браузерная среда. Минимально проверить:

1. `/`, `/login/` и `/register/` корректно открываются; без авторизации защищённые данные не показываются.
2. Вход демо-пользователем открывает список его задач; выход очищает авторизованное состояние.
3. Создание задачи, назначение исполнителя, редактирование создателем, изменение статуса исполнителем, добавление комментария и запрещённое действие работают ожидаемо.
4. Ошибки API и пустой список дают читаемую обратную связь.
5. Все три режима темы работают; выбор сохраняется после перезагрузки; системный режим реагирует на настройку ОС.
6. Основные сценарии доступны в viewport мобильного телефона, планшета и desktop без обрезанных элементов или горизонтальной прокрутки страницы.

Если полноценный браузерный smoke-check выполнить невозможно, не утверждать, что он пройден: описать, что проверено автоматическими тестами, а что осталось проверить вручную.
