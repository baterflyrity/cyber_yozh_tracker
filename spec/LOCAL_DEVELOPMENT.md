# Локальный запуск и E2E-данные

Этот документ дополняет `spec/SPEC.md` и задаёт обязательный сценарий локального запуска через Docker Compose. Цель — чтобы проверяющий мог открыть современный браузерный интерфейс и API, а затем пройти E2E-сценарий с несколькими аккаунтами без ручного наполнения базы. Главная страница UI должна быть доступна по `http://localhost:8000/`; маршруты входа/регистрации и полный набор URL должны быть согласованы с README. Подробные UI smoke-checks определены в `spec/FRONTEND.md`, требования к README — в `spec/DOCUMENTATION.md`.

## 1. Docker Compose

Добавить:

- `Dockerfile` для Django-приложения;
- `compose.yaml` (допустимо имя `docker-compose.yml`) с одним сервисом приложения;
- `docker/entrypoint.sh` либо эквивалентный стартовый механизм;
- `.dockerignore`;
- именованный volume для файла SQLite, например `/app/data/db.sqlite3`.

Отдельный контейнер PostgreSQL не нужен: используем SQLite, чтобы ограничить инфраструктурную сложность тестового задания. Путь к базе должен задаваться переменной окружения, например `DJANGO_DB_PATH`, и внутри Compose указывать на файл в именованном volume, а не на файл в слое контейнера.

Порт приложения должен быть опубликован на host, например `8000:8000`. Development server должен слушать `0.0.0.0:8000` внутри контейнера. Compose предназначен только для локальной разработки и тестирования, не для production-развёртывания.

## 2. Последовательность запуска

`docker compose up --build` должен выполнять следующий порядок:

1. Подготовить каталог и права для SQLite-файла.
2. Применить миграции (`python manage.py migrate --noinput`).
3. Если явно включён флаг загрузки демо-данных, выполнить `python manage.py seed_demo_data`.
4. После успешного выполнения предыдущих шагов запустить development server.

Если миграции или seed-команда завершаются с ошибкой, контейнер не должен продолжать запуск так, будто всё прошло успешно. Не скрывать ошибку миграций и не игнорировать ненулевой exit code.

Seed-команда должна быть **идемпотентной**: повторный запуск не создаёт дубликатов пользователей или задач. Реализовать её как Django management command, а не выполнять SQL вставки из `docker-compose.yml`. Для создания/обновления демо-объектов использовать стабильные usernames и детерминированные уникальные признаки задач.

Демо-данные должны автоматически загружаться в Compose по умолчанию, если предусмотренный флаг выставлен в локальной Compose-конфигурации. За пределами этой конфигурации seed не должен запускаться автоматически. Команда должна отказываться работать при `DEBUG=False` (или иметь равнозначную явную защиту от запуска в production). Не добавлять тестовые пароли в production settings.

## 3. Демо-пользователи

Создать три пользователя с фиксированными для локального окружения учётными данными:

| Username | Пароль | Роль в сценариях |
|---|---|---|
| `demo_owner` | `DemoOwner123!` | Создаёт задачи и управляет ими |
| `demo_worker` | `DemoWorker123!` | Исполнитель задачи; проверяет возможность изменить только статус |
| `demo_outsider` | `DemoOutsider123!` | Не является участником конкретной задачи; проверяет запрет доступа |

Пароли должны создаваться через штатные средства Django (`create_user`/`set_password`), никогда не храниться в открытом виде в базе. Логины и пароли можно явно документировать в README, потому что они предназначены только для локального тестового окружения. README должен предупредить: эти учётные данные небезопасны и не должны использоваться за пределами локального окружения.

Для seed-аккаунтов не выдавать `is_staff` или `is_superuser`. Команда не должна менять пароль уже существующего пользователя с тем же username, если это может неожиданно затронуть реальные данные. Учитывая, что это dev-only команда, допустимы `get_or_create` и безопасное создание недостающих пользователей; поведение при существующих пользователях должно быть документировано и повторный запуск должен оставаться безопасным.

## 4. Демо-задачи

Seed должен создавать минимум три задачи с устойчивыми заголовками и связями:

1. **«Подготовить демонстрационный API-сценарий»** — создана `demo_owner`, назначена `demo_worker`, не выполнена. Используется для основного E2E сценария.
2. **«Задача только для владельца»** — создана `demo_owner`, не назначена исполнителю. Проверяет, что `demo_worker` и `demo_outsider` не могут её прочитать.
3. **«Моя задача исполнителя»** — создана `demo_worker`, без исполнителя или назначена самому `demo_worker`. Проверяет работу со своей задачей.

Как минимум одна задача должна иметь тестовый комментарий от участника. Поддерживать ссылочную целостность; повторный запуск не должен порождать дополнительные копии этих задач и комментария. Demo данные не должны фиксироваться в репозитории как дамп с хешами паролей или как локальный SQLite-файл.

## 5. E2E-сценарий, описать в README

После `docker compose up --build` проверить через Swagger UI (`/api/docs/`) или curl:

1. Войти как `demo_owner` через JWT endpoint и получить access token.
2. Получить список задач: owner видит созданные им задачи.
3. Открыть основную задачу и проверить, что `demo_worker` назначен исполнителем.
4. Добавить комментарий от имени владельца.
5. Войти как `demo_worker`, получить назначенную задачу и установить `is_completed=true`.
6. Проверить, что `demo_worker` не может изменить `title`, `description`, `assigned_to` или удалить задачу.
7. Войти как `demo_outsider` и проверить, что задача не возвращается в списке и недоступна по detail endpoint.
8. Попробовать изменить/удалить чужой комментарий и убедиться, что API отклоняет операцию.

README должен включать команды/примеры запроса для входа и хотя бы одного запрещённого действия, с ожидаемыми статус-кодами. Дополнительно README должен содержать браузерный UI smoke-check, включая адаптивные размеры и темы; подробный перечень см. `spec/FRONTEND.md`. Не требуется добавлять Selenium/Playwright только ради тестового задания, если это заметно раздувает стек, но обычный UI smoke-check следует выполнить вручную в доступном браузере. Автоматизированные API-тесты обязательны; описанный E2E-сценарий дополняет, но не заменяет их.

## 6. Полезные команды для README

Документировать и проверить фактические команды, эквивалентные следующим:

```bash
# Запуск приложения и заполнение демо-данными
docker compose up --build

# Логи сервиса
docker compose logs -f web

# Тесты внутри контейнера (конкретную команду адаптировать под выбранный test runner)
docker compose exec web pytest

# Остановка без удаления данных
docker compose down

# Полный сброс локальной SQLite-базы и всех данных volume
docker compose down -v
```

Использовать стандартное написание команды `docker compose` в нижнем регистре. Если сервис будет назван не `web`, привести команды в README в соответствие с реальным именем. После `down -v` следующий запуск должен создать чистую базу, применить миграции и заново загрузить демо-данные.

## 7. Browser UI smoke-check

После старта Compose открыть `http://localhost:8000/` в браузере. Пройти checklist из `spec/FRONTEND.md`: вход под демо-пользователем, просмотр доступных задач, создание/назначение/завершение/комментарии, ошибки/пустые состояния, переключение тем и узкие мобильные размеры. В README записать результат и не отмечать непроверенные действия как успешные. Если в среде агента нет браузера, явно отметить эту проверку как ручной шаг для проверяющего.

## 8. Безопасность и воспроизводимость

- `.env`, реальные секреты, SQLite-файлы и токены не коммитить.
- В репозитории хранить только `.env.example` с безопасными примерами переменных.
- `.dockerignore` должен исключать `.git`, `.venv`, кэши тестов, `.env`, локальную БД и прочие артефакты.
- Фиксированные демо-пароли допустимы только для явно локального демонстрационного окружения, не для production.
- Контейнер должен завершаться с ненулевым кодом, если миграции/seed не удались.
- Убедиться, что код и тесты работают как при обычном локальном запуске, так и в Compose-контейнере.
