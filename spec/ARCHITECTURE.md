# Архитектурная спецификация

Этот документ дополняет `spec/SPEC.md`. Его цель — явно разделить модели данных, доменную логику и HTTP API, не превращая небольшой тестовый проект в избыточно сложную архитектуру.

## 1. Обязательные границы слоёв

### Models / persistence

Django models определяют поля, связи, индексы, ограничения базы данных и простые значения по умолчанию. Модели не должны принимать `request`, возвращать HTTP-ответы или зависеть от DRF. Не переносить в модели многошаговые сценарии, которые связывают несколько сущностей.

### Domain services

`services.py` (либо небольшой пакет `services/`) содержит операции изменения состояния и бизнес-правила, в том числе:

- создание задачи с `created_by`, равным текущему пользователю;
- редактирование задачи создателем;
- изменение только `is_completed` исполнителем;
- назначение активного пользователя;
- добавление комментария участником задачи;
- изменение/удаление комментария с проверкой авторства и доступа к задаче.

Сервисам передаются обычные аргументы (`actor`, объект/ID, валидированные данные); они не должны зависеть от `HttpRequest`, `Response`, `APIView` или других HTTP/DRF объектов. Для атомарных операций использовать `transaction.atomic` там, где это оправдано.

Все изменения доменного состояния из API должны проходить через service-функции. Не оставлять альтернативные endpoint-код-пути, которые напрямую изменяют несколько моделей в обход правил.

### Selectors / query layer

`selectors.py` содержит запросы на чтение и формирование queryset:

- задачи, видимые данному пользователю;
- поиск, фильтры, сортировка и пагинация;
- комментарии для доступной пользователю задачи;
- поиск активных пользователей для справочника назначения.

Не использовать общий `Task.objects.all()` для пользовательского списка или detail endpoint без ограничения доступности. Фильтрация доступа к объекту должна быть централизована и переиспользуема.

### API / transport

В `api/` находятся:

- `serializers.py` — транспортная валидация и сериализация полей;
- `permissions.py` — DRF permission classes для грубого уровня доступа и вызова общих проверок, если они нужны API;
- `views.py` — перевод HTTP-запроса в вызов selector/service и результата в HTTP-ответ;
- `urls.py` — маршруты.

Views не должны содержать бизнес-ветвления вроде «если пользователь исполнитель, разрешить только поле статуса»; такая логика относится к доменному слою. Serializer не должен быть единственной защитой бизнес-инвариантов, поскольку сервисы могут вызываться другими частями приложения.

Не дублировать одно и то же правило авторизации в нескольких независимых реализациях. Если view/permission и service должны проверить одну и ту же политику, они должны использовать общий policy helper или сервисный метод.

## 2. Веб-интерфейс как отдельный transport-слой

Браузерный интерфейс является отдельным presentation/transport слоем, но не отдельным frontend-сервисом. Django templates отдают HTML shell, static assets (CSS и vanilla JavaScript) взаимодействуют с REST API через `fetch`. Web views отвечают только за отображение страниц (например, dashboard и login page); они не дублируют бизнес-операции, фильтрацию доступа или запись в модели. Все операции данных должны проходить через существующий API и доменные services/selectors. Не использовать Django templates для прямого вывода объектов без соответствующей проверки доступа.

Frontend JS не должен становиться источником истины для прав доступа: кнопки можно скрывать для удобства, но API всегда повторно проверяет права. Не рендерить пользовательский текст с помощью небезопасного `innerHTML`; не добавлять секреты и токены в HTML templates или логи. Детали UI и хранения темы определены в `spec/FRONTEND.md`.

## 3. Рекомендуемая структура

Допускается адаптация под существующий репозиторий, но сохраните понятные границы:

```text
.
├── AGENTS.md
├── spec/
│   ├── SPEC.md
│   ├── ARCHITECTURE.md
│   ├── FRONTEND.md
│   ├── DOCUMENTATION.md
│   └── LOCAL_DEVELOPMENT.md
├── config/
│   ├── settings.py (или пакет settings/)
│   ├── urls.py
│   ├── asgi.py
│   └── wsgi.py
├── apps/
│   ├── users/
│   │   ├── api/
│   │   │   ├── serializers.py
│   │   │   ├── views.py
│   │   │   └── urls.py
│   │   ├── services.py
│   │   ├── tests/
│   │   └── ...
│   └── tasks/
│       ├── models.py
│       ├── services.py
│       ├── selectors.py
│       ├── api/
│       │   ├── serializers.py
│       │   ├── permissions.py
│       │   ├── views.py
│       │   └── urls.py
│       ├── management/commands/seed_demo_data.py
│       ├── migrations/
│       └── tests/
├── web/                        # только template/page views, без доменной логики
├── templates/                   # Django templates (shell, login, dashboard)
├── static/                      # CSS, vanilla JS, icons
├── Dockerfile
├── compose.yaml (или docker-compose.yml)
├── docker/entrypoint.sh
├── .dockerignore
├── .env.example
├── README.md
├── docs/                        # пользовательская документация, если нужна отдельно
└── pyproject.toml (или существующие файлы зависимостей)
```

Это рекомендация, а не требование создать каждый возможный файл. Например, если регистрация пользователя проста, допустим один `users/services.py`; если маленький `users` app можно встроить в существующую структуру без смешивания слоёв — не добавляйте пакет ради пакета. Не храните спецификации в корне: все документы требований, кроме `AGENTS.md`, должны лежать в `spec/`.

## 4. Импортные зависимости

Предпочтительное направление зависимостей:

`REST API views → serializers / selectors / services → models`; `web page views → templates/static shell`, а browser JS вызывает REST API

Модели не импортируют API. Сервисы не импортируют views/serializers. Selectors не формируют HTTP-ответы. Сериализаторы не должны вызывать HTTP endpoints.

## 5. Обработка ошибок

Доменные ошибки (например, запрет действия или некорректная доменная операция) должны преобразовываться в предсказуемые DRF HTTP-ответы на границе API. Не перехватывать широким `except Exception` ошибки, чтобы маскировать дефекты. Использовать атомарность для операций, которые изменяют несколько связанных объектов.

## 6. Чего не делать

- Не помещать всю бизнес-логику в `views.py` или сериализаторы. Это относится также к HTML page views: они должны лишь отдавать шаблоны/статику.
- Не реализовывать generic repository pattern поверх Django ORM без практической необходимости.
- Не создавать отдельные микросервисы, CQRS, event bus, Celery или фоновые очереди.
- Не вводить абстракции только для увеличения количества слоёв.
- Не ослаблять правила доступа для удобства тестового наполнения. Демо-данные должны создаваться management command и использовать штатные модели/хелперы.
