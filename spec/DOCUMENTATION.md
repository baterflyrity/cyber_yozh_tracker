# Спецификация документации и README

Этот документ определяет критерии качества документации. README — часть результата тестового задания и один из главных способов оценки решения. Он должен быть понятным разработчику, который клонировал репозиторий и впервые видит проект.

## 1. Обязательные документы

### `README.md` в корне

README должен быть самодостаточным для основного сценария запуска через Docker Compose. Читатель должен без догадок понять, что делает проект, как его запустить, как проверить API и UI, как выполнить тесты и какие ограничения доступа реализованы.

### `docs/ARCHITECTURE.md` (рекомендуется, если подробное описание делает README чрезмерно длинным)

Может описывать структуру проекта, границы `models` / `services` / `selectors` / API / web presentation, направления зависимостей, основные потоки обработки и принятые упрощения. Не копировать туда спецификации из `spec/`; это должна быть документация именно реализованного кода.

Документы требований агенту остаются в `spec/`. Не перемещать `spec/*.md` в `docs/` и не создавать дублирующие версии спецификаций.

## 2. Обязательное содержание README

README должен включать следующие разделы, в логичном порядке:

1. **Название и назначение:** кратко описать приложение, возможности и используемый стек.
2. **Функциональность:** задачи, назначение пользователей, статусы, комментарии, JWT API и браузерный интерфейс.
3. **Демонстрация UI:** локальный URL, вход/регистрация, ключевые действия и выбор темы System/Light/Dark (на русском интерфейсе — Системная/Светлая/Тёмная).
4. **Быстрый запуск через Docker Compose:** необходимые версии Docker Engine/Desktop и Compose plugin, команда запуска, ожидаемые сообщения/состояние сервиса, адреса приложения и API-документации.
5. **Демо-данные:** все usernames и пароли для локального окружения, роль каждого пользователя, какие задачи/комментарии создаются и какие сценарии они демонстрируют. В явном виде предупредить, что эти пароли предназначены только для локальной разработки.
6. **Пошаговый E2E-сценарий:** минимум один успешный и один запрещённый сценарий. Привести точные `curl`-примеры входа/получения JWT и вызова API, объяснить, куда подставлять access token, показать ожидаемый статус-код и что должно быть видно в ответе. Подробный набор сценариев определён в `spec/LOCAL_DEVELOPMENT.md`.
7. **UI smoke-check:** список шагов для браузерной проверки, включая login/logout, создание/изменение/назначение задачи, статус, комментарии, ошибки и все три темы на мобильном и desktop viewport.
8. **Запуск тестов:** точные команды тестов и линтера вне Docker и внутри контейнера; описать, что именно покрывают тесты и каков ожидаемый результат. Сверить названия команд с реальными скриптами и зависимостями.
9. **Полезные Docker-команды:** логи, статус, запуск тестов, остановка контейнера, повторный старт и полный сброс данных через удаление volume. Объяснить, что `docker compose down -v` удаляет сохранённую SQLite-базу и связанные локальные данные.
10. **Запуск без Docker:** список требований к Python/менеджеру зависимостей, создание окружения, установка зависимостей, настройка `.env` из `.env.example`, миграции, seed-команда (если нужна вручную), запуск сервера, тесты и static assets.
11. **API reference:** ссылки на OpenAPI schema, Swagger UI и Redoc; объяснить JWT Bearer header и основные endpoint-группы. Не нужно вручную дублировать весь OpenAPI-контракт в README.
12. **Правила доступа:** кто видит задачи, кто их создаёт/редактирует/удаляет, полномочия исполнителя, правила комментариев и ожидаемое поведение для постороннего пользователя.
13. **Структура проекта:** краткая карта ключевых модулей с пояснением, где модели, services, selectors, API, web templates/static, тесты и seed-команда.
14. **Конфигурация и безопасность:** таблица важных переменных окружения, безопасные примеры `.env.example`, запрет на реальные секреты и назначение демо-паролей.
15. **Известные ограничения/допущения:** например, SQLite рассчитана на это тестовое приложение; Compose dev server не предназначен для production.

Добавить оглавление, если документ получается длинным. Использовать реальные пути, команды, URL и имена контейнеров из реализации.

## 3. Качество команд и примеров

- Каждая приведённая команда должна соответствовать фактическому проекту. Например, если Compose service называется `web`, только тогда использовать `docker compose exec web ...`.
- Не оставлять placeholders вроде `YOUR_TOKEN`, `TODO`, `...` в местах, которые должны быть исполняемыми без объяснения. Для токена можно явно показать переменную shell и команду, которая её заполняет из ответа JWT, либо указать, как безопасно скопировать token в заголовок.
- Для API-примеров показать метод, URL, нужные заголовки, request body и ожидаемый статус. Достаточно набора примеров для основных операций; не нужно копировать каждый endpoint.
- У успешных и запрещённых операций указать, почему они разрешены/запрещены. Для запрещённых запросов привести ожидаемый статус-код и краткий смысл ответа.
- Если команды отличаются для PowerShell и POSIX shell, выбрать один основной вариант и явно назвать оболочку; при разумном объёме приложить эквивалент для другой распространённой среды.
- Не включать действительные API-токены, секретный ключ Django, хеши паролей, локальную базу или вывод, содержащий секреты.
- Не утверждать, что тесты, линтер, Docker build или UI smoke-check прошли, если они не запускались. Если среда не позволила выполнить проверку, сообщить об этом явно и указать оставшийся шаг.

## 4. Docker Compose и повторяемое тестирование

README обязан объяснить полный цикл проверки, а не только команду запуска:

1. Что требуется установить.
2. Как запустить контейнер и дождаться готовности приложения.
3. Где открыть UI, Swagger UI, Redoc и OpenAPI schema.
4. Какие демо-учётные данные использовать.
5. Как повторить успешный и запрещённый API-сценарии.
6. Как запустить автоматические тесты/линтер внутри контейнера.
7. Как посмотреть логи и диагностировать ошибку миграций/seed.
8. Как остановить приложение, сохранить данные и при необходимости выполнить полный сброс volume.
9. Как убедиться, что повторный запуск не создаёт дубликаты демо-пользователей, задач и комментариев.

Указать, что демо-seed ограничен локальной конфигурацией, идемпотентен и не должен запускаться на production-данных.

## 5. Обязательная проверка документации перед сдачей

Перед завершением работы агент должен:

- пройти README как новый пользователь и проверить все команды в чистом окружении, насколько позволяет текущая среда;
- выполнить основной Docker Compose сценарий, применить миграции, подтвердить загрузку seed-данных и доступность приложения;
- запустить команды тестов и линтера, которые указаны в README;
- проверить реальные пути `/`, login/register, `/api/docs/`, `/api/redoc/`, `/api/schema/`;
- пройти E2E-чек-лист из `spec/LOCAL_DEVELOPMENT.md` и UI smoke-check из `spec/FRONTEND.md` либо явно перечислить непроверенные пункты;
- проверить `git diff` на отсутствующие документы, устаревшие ссылки, placeholders, секреты и локальные артефакты.

README и документация должны описывать реализованный результат, а не желаемую архитектуру. Если реализация отличается от спецификации по объективной причине, обновить документацию и указать отклонение в финальном отчёте, не скрывая его.
