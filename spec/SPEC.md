# CyberYozh — Task Manager API: основная спецификация

## 1. Цель

Разработать готовое к проверке веб-приложение для управления задачами на Django и Django REST Framework. Результат включает корректный REST API, небольшой современный адаптивный веб-интерфейс, разделение моделей, доменной логики и HTTP endpoints, автоматические тесты, Docker Compose с демо-данными и подробную документацию/README. Интерфейс должен поддерживать системную, светлую и тёмную темы. Не создавать отдельный frontend-сервис или сложный SPA-фреймворк: использовать Django templates и обычные CSS/JavaScript, отдаваемые тем же Django-приложением. Swagger UI и browsable API остаются доступны для проверки API. Архитектурные границы описаны в `spec/ARCHITECTURE.md`, требования к интерфейсу — в `spec/FRONTEND.md`, локальный запуск и демо-данные — в `spec/LOCAL_DEVELOPMENT.md`, требования к README и дополнительной документации — в `spec/DOCUMENTATION.md`.

Приоритеты: корректность бизнес-правил и доступа → тесты → понятная архитектура → документация → необязательные улучшения. Не добавлять функциональность, которой нет в этом документе, если она заметно увеличивает объём или сложность решения.

## 2. Технологический стек

- Python 3.12+; если в репозитории уже выбрана совместимая версия, не менять её без необходимости.
- Django 5.2 LTS и Django REST Framework.
- SQLite как основная БД: проект должен запускаться локально без отдельного сервера БД. Для контейнерного запуска SQLite-файл хранить в именованном Docker volume.
- JWT-аутентификация через `djangorestframework-simplejwt`.
- API-схема и документация через `drf-spectacular` (Swagger UI и Redoc).
- `uv` и `pyproject.toml`, если репозиторий не использует другой менеджер зависимостей. Если в репозитории уже есть рабочая инфраструктура, сохранить её и не создавать параллельный способ установки.
- `pytest` + `pytest-django` для тестов, Ruff для проверки стиля. Допускается использовать уже настроенные в репозитории аналоги.
- Docker и Docker Compose обязательны для воспроизводимого локального запуска и E2E-проверок с демо-данными.
- Frontend: Django templates, семантический HTML, CSS и vanilla JavaScript; не требуется Node.js, npm или отдельная сборка frontend.

Не подключать PostgreSQL, Redis, Celery, OAuth, React/Vue/Angular, отдельный frontend-сервис или другие необязательные инфраструктурные компоненты: в рамках задания они не нужны. Docker Compose должен запускать только Django-приложение и использовать SQLite в именованном volume; отдельный контейнер БД не нужен. Веб-интерфейс и API должны быть доступны с одного origin.

## 3. Область функциональности

Пользователь должен иметь возможность работать с ключевыми функциями через браузерный UI, а не только через Swagger. Подробные страницы, состояния и требования к адаптивности указаны в `spec/FRONTEND.md`. API остаётся полноценным самостоятельным интерфейсом; frontend не должен быть единственным местом реализации правил доступа.

### 3.1. Пользователи и аутентификация

1. Пользователь может зарегистрироваться с уникальным `username` и паролем. Email необязателен, если это упрощает регистрацию; если он включён, правила уникальности должны быть явно заданы.
2. Пароль должен хешироваться штатными средствами Django. Нельзя возвращать пароль или его хеш в API-ответах.
3. API использует JWT access/refresh tokens.
4. Все endpoints задач, комментариев и списка пользователей требуют аутентификации.
5. Endpoint регистрации и выдачи токенов доступны без JWT.
6. Нельзя позволять клиенту назначать себе `id`, `is_staff`, `is_superuser`, `created_by` или другие привилегированные поля через API.
7. Для назначения задачи другому пользователю предоставляется аутентифицированный справочник пользователей, возвращающий только необходимую информацию (как минимум `id` и `username`, без паролей и без лишних персональных данных).

### 3.2. Задачи

У задачи должны быть следующие поля:

- `id` — первичный ключ, только чтение;
- `title` — обязательная строка длиной 1–200 символов;
- `description` — необязательный текст, по умолчанию пустой;
- `created_by` — автор/создатель задачи, определяется сервером из `request.user`, только чтение;
- `assigned_to` — назначенный пользователь или `null`, можно менять при наличии прав;
- `is_completed` — boolean, по умолчанию `false`;
- `created_at` и `updated_at` — даты создания и последнего изменения, только чтение.

Новая задача всегда создаётся от имени текущего пользователя независимо от тела запроса. Можно создать задачу без исполнителя (`assigned_to: null`) и назначить её на себя или другого активного зарегистрированного пользователя.

### 3.3. Комментарии

У комментария должны быть следующие поля:

- `id` — первичный ключ, только чтение;
- `task` — связанная задача, определяется вложенным URL и не может быть подменена телом запроса;
- `author` — автор, определяется сервером из `request.user`, только чтение;
- `body` — обязательный текст длиной 1–5000 символов;
- `created_at` и `updated_at` — даты, только чтение.

Участники задачи могут просматривать комментарии и добавлять новые. Автор комментария может редактировать или удалять только собственный комментарий. При удалении задачи связанные комментарии удаляются каскадно.

## 4. Правила доступа — обязательные

Не полагаться на скрытие кнопок или клиентскую проверку: все ограничения реализовать и проверить на сервере.

1. **Видимость задачи:** пользователь видит задачу, только если он её создал или она назначена ему. Список задач должен возвращать только доступные текущему пользователю задачи.
2. **Создание:** любой аутентифицированный пользователь может создать задачу. `created_by` назначается сервером.
3. **Редактирование задачи:** создатель может изменять `title`, `description`, `assigned_to` и `is_completed`, а также удалять задачу.
4. **Исполнитель:** назначенный пользователь может менять только `is_completed` (отмечать задачу выполненной или снова открывать её). Попытка изменить `title`, `description`, `assigned_to` или удалить задачу должна отклоняться.
5. **Участники:** создатель и текущий исполнитель могут просматривать задачу, её комментарии и добавлять комментарии. После переназначения прежний исполнитель теряет доступ, если он не является создателем.
6. **Комментарии:** редактировать/удалять комментарий может только его автор, причём только пока у него есть доступ к связанной задаче. Нельзя переносить комментарий на другую задачу через `PATCH`/`PUT`.
7. **Анонимные запросы:** защищённые endpoints не должны возвращать приватные данные; использовать корректные ответы 401/403. Для объектов, которые не входят в доступный пользователю queryset, допустимо возвращать 404, чтобы не раскрывать факт существования чужой задачи; поведение должно быть последовательным и задокументированным.
8. **Назначение исполнителя:** разрешать назначать только существующего активного пользователя. Некорректный или неактивный пользователь должен приводить к валидационной ошибке, а не к 500.

Если ограничения доступа конфликтуют с поведением стандартного `ModelViewSet`, добавить явные permissions/переопределения методов. Не разрешать массовое изменение полей через сериализатор.

## 5. REST API

Префикс API: `/api/`. JSON — основной формат запросов и ответов. Стандартные HTTP-методы и статус-коды должны соответствовать операциям.

### Аутентификация

| Метод | Endpoint | Назначение | Доступ |
|---|---|---|---|
| `POST` | `/api/auth/register/` | Регистрация пользователя | Публичный |
| `POST` | `/api/auth/token/` | Получение JWT access/refresh | Публичный |
| `POST` | `/api/auth/token/refresh/` | Обновление access token | По refresh token |
| `GET` | `/api/auth/me/` | Информация о текущем пользователе (`id`, `username`, при необходимости `email`) | Аутентифицированный |
| `GET` | `/api/users/?search=<query>` | Справочник пользователей для назначения задач | Аутентифицированный |

### Задачи

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/tasks/` | Список доступных текущему пользователю задач |
| `POST` | `/api/tasks/` | Создание задачи |
| `GET` | `/api/tasks/{id}/` | Получение задачи |
| `PUT` | `/api/tasks/{id}/` | Полное обновление создателем задачи |
| `PATCH` | `/api/tasks/{id}/` | Частичное обновление с учётом правил доступа |
| `DELETE` | `/api/tasks/{id}/` | Удаление создателем задачи |

Поддержать фильтр `?is_completed=true` / `?is_completed=false`, поиск `?search=<text>` по заголовку и описанию и сортировку по ограниченному списку полей, например `?ordering=created_at` или `?ordering=-updated_at`. Если пагинация включена, описать её формат и параметры в README и OpenAPI. Разумный размер страницы по умолчанию — 20 элементов.

### Комментарии

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/tasks/{task_id}/comments/` | Список комментариев к доступной задаче |
| `POST` | `/api/tasks/{task_id}/comments/` | Добавление комментария к доступной задаче |
| `GET` | `/api/tasks/{task_id}/comments/{id}/` | Получение комментария в контексте задачи |
| `PATCH` | `/api/tasks/{task_id}/comments/{id}/` | Изменение собственного комментария |
| `DELETE` | `/api/tasks/{task_id}/comments/{id}/` | Удаление собственного комментария |

Если выбранная реализация не поддерживает `PUT` для комментариев, это не проблема: достаточно `PATCH` для редактирования. Вложенный `task_id` должен проверяться при каждом запросе: нельзя обратиться к комментарию одной задачи через URL другой задачи.

### Формат ответов и ошибок

- Возвращать сериализованные объекты и стандартные HTTP status codes.
- Ошибки валидации должны быть понятными и иметь стабильную структуру DRF.
- `POST` при успешном создании возвращает `201`, `DELETE` — `204`, неверные данные — `400`, неаутентифицированный доступ — `401` (с учётом настроенного JWT authentication), а отсутствие прав — `403` или последовательный `404` для объектов вне доступного queryset.
- Не возвращать stack trace, секреты, пароли или внутреннюю информацию сервера в API-ответах.

## 6. Документация API

Сгенерировать OpenAPI-схему средствами `drf-spectacular` и предоставить:

- `/api/schema/` — OpenAPI schema;
- `/api/docs/` — Swagger UI;
- `/api/redoc/` — Redoc.

Документация должна описывать JWT Bearer authentication, endpoints, поля запросов/ответов, ошибки, фильтры, пагинацию и основные ограничения доступа. Необходимо проверить, что схема генерируется и страницы документации открываются.

## 7. Веб-интерфейс и темы

- Реализовать полноценный минимальный интерфейс для входа/регистрации, списка задач, создания и редактирования задачи, назначения исполнителя, изменения статуса, просмотра и добавления комментариев.
- После входа пользователь должен видеть только задачи, доступные ему по серверным правилам доступа. Запреты должны обеспечиваться API, а не только скрытием элементов интерфейса.
- Интерфейс должен быть современным, визуально цельным, адаптивным для мобильных телефонов, планшетов и desktop; подробные требования — в `spec/FRONTEND.md`.
- Добавить выбор темы **Системная / Светлая / Тёмная**. В системном режиме учитывать `prefers-color-scheme`; сохранять выбор пользователя между перезагрузками; корректно обновлять системную тему, если выбран системный режим.
- Основные действия должны иметь состояния загрузки, успеха, пустого списка и ошибки; формы должны показывать доступные сообщения валидации.
- Соблюдать доступность: семантическая разметка, управление с клавиатуры, видимый focus, читаемый контраст, связанные подписи полей и aria-атрибуты там, где нужны.
- Не выводить данные пользователей или задачи за пределами прав текущего пользователя. Не вставлять пользовательский текст в DOM через небезопасный `innerHTML`; использовать безопасные DOM API и экранирование.

## 8. Архитектура и качество кода

Обязательно отделить persistence-модели, доменные правила/операции и HTTP API endpoints друг от друга. Соблюдать структуру и границы, определённые в `spec/ARCHITECTURE.md`. Endpoint/view не должен содержать бизнес-правила или напрямую координировать несколько моделей; он должен преобразовывать HTTP-запрос, вызывать selector/service и формировать HTTP-ответ.

- Django models описывают структуру и связи данных, простые ограничения и значения по умолчанию.
- Доменная логика записи и проверка допустимости операций находятся в сервисном слое (`services.py` или небольшом модуле `services/`).
- Получение, фильтрация и ограничение queryset находятся в selector/query layer (`selectors.py`), чтобы список и detail endpoint не содержали дублирующуюся логику выборки.
- REST API отдельно организован в модуле `api/`: serializers, permissions, views и urls. Сериализаторы отвечают за транспортную валидацию/представление данных, но не должны становиться единственным местом бизнес-правил.
- Не внедрять generic repository pattern, CQRS, event bus или чрезмерную абстракцию для данного MVP.

Дополнительные требования:

- Следовать PEP 8; использовать Ruff для линтинга.
- Не дублировать правила доступа в нескольких местах без необходимости; общие policy checks должны быть централизованы или вызываться из одного доменного слоя.
- Не размещать всю логику в одном файле.
- Добавить осмысленные имена, небольшие методы и комментарии только там, где причина решения неочевидна.
- Секретный ключ, `DEBUG`, `ALLOWED_HOSTS` и путь к SQLite-файлу читать из переменных окружения. Не коммитить `.env` и секреты; добавить `.env.example` без реальных секретов.
- Добавить миграции и проверить, что новая база разворачивается командой миграций.
- Не использовать `csrf_exempt` как обход проблем аутентификации.
- Не менять файлы и настройки, не относящиеся к заданию, без необходимости.

## 9. Тестирование — обязательное

Автоматические тесты должны проверять как успешные сценарии, так и ограничения доступа. Использовать Django test client/DRF `APITestCase` или pytest/pytest-django — единообразно по всему проекту.

Минимальный набор:

1. Регистрация, вход по JWT, обновление токена и получение текущего пользователя.
2. Неаутентифицированный пользователь не может читать или изменять задачи и комментарии.
3. Создание задачи: создатель берётся из текущего пользователя, а попытка подменить его через payload игнорируется или отклоняется.
4. Создатель может получить, обновить и удалить свою задачу.
5. Исполнитель видит назначенную ему задачу и может менять `is_completed`.
6. Исполнитель не может менять заголовок/описание/исполнителя или удалять задачу.
7. Посторонний пользователь не видит чужую задачу в списке и не может получить её по ID.
8. Назначение существующего пользователя и обработка неизвестного/неактивного пользователя.
9. Фильтрация по `is_completed`, поиск и пагинация, если они реализованы.
10. Участники задачи могут смотреть и создавать комментарии; посторонние не могут.
11. Автор комментария может изменить/удалить свой комментарий, другой пользователь не может.
12. Вложенный `task_id` проверяется; нельзя манипулировать комментарием через чужую задачу.
13. Валидация обязательного заголовка задачи и тела комментария, включая ограничения длины.
14. OpenAPI-схема доступна и генерируется без ошибок.
15. Browser/page endpoints для `/`, `/login/` и `/register/` доступны; CSS/JS static assets отдаются без ошибок.
16. Если frontend logic покрыта автоматическими тестами, проверить переключение режимов темы и хранение пользовательского выбора; в любом случае выполнить ручной UI smoke-check по `spec/FRONTEND.md`, когда доступен браузер.

Не ограничиваться тем, что тесты проходят: проверить права доступа отдельными тестами на запрещённые действия. Не отключать тесты и не ослаблять assertions ради зелёного результата.

## 10. README, Docker Compose и воспроизводимость

README.md — обязательный полноценный документ для разработчика и проверяющего, а не краткая заглушка. Он должен позволять человеку, который впервые открыл репозиторий, с нуля запустить приложение, пользоваться веб-интерфейсом и API, выполнить тесты и проверить ограничения доступа. Полные требования собраны в `spec/DOCUMENTATION.md`. Включить:

1. Краткое описание возможностей и принятых решений.
2. Требования к Python и команды создания окружения/установки зависимостей для запуска без Docker.
3. Инструкцию настройки переменных окружения на основе `.env.example`.
4. Команды миграций и запуска development server без Docker.
5. Основной рекомендуемый сценарий Docker Compose: `docker compose up --build`, адреса API/Swagger/Redoc и команды просмотра логов/остановки.
6. Описание тестовых пользователей и задач, доступных после запуска Compose, включая логины/пароли, назначение каждого пользователя и предупреждение, что эти учётные данные допустимы только для локальной разработки.
7. Команды запуска тестов и линтера как локально, так и в контейнере, где применимо.
8. Ссылки на Swagger, Redoc и OpenAPI schema.
9. Примеры регистрации двух пользователей, получения JWT, создания задачи, назначения её другому пользователю, отметки выполнения и добавления комментария. Для примеров HTTP-запросов можно использовать `curl`.
10. Описание модели доступа: кто видит задачу, кто редактирует её, кто может завершить её и кто управляет комментариями.
11. Пошаговый локальный E2E-сценарий в Docker Compose с curl-командами, ожидаемыми статус-кодами и примерами как успешного, так и запрещённого действия. Не ограничиваться фразой «проверьте вручную».
12. Краткое руководство по UI: вход, фильтрация/поиск задач, создание, назначение, выполнение, комментарии и переключение тем.
13. Команды безопасного сброса локальных демо-данных/volume и предупреждение, что удаление volume удаляет сохранённую SQLite-базу.
14. Ссылки на дополнительную документацию в `docs/`, если она создана, и на спецификации в `spec/`.
15. Любые допущения или ограничения, которые влияют на использование API или UI.

Docker Compose должен выполнять миграции автоматически при старте контейнера, затем идемпотентно загружать демонстрационные данные и только после успешного выполнения запускать development server. Сценарий описан в `spec/LOCAL_DEVELOPMENT.md`. Демо-пользователи/данные никогда не должны загружаться автоматически в production-конфигурации.

Инструкции должны быть подробными и проверенными на практике. Не указывать команды, которые не запускались или не работают в текущем проекте. README должен содержать оглавление, краткую карту проекта, разделы запуска через Docker и без Docker, тестирования, E2E-проверки, API-документации и известных ограничений. Подробное описание архитектуры, тестовых сценариев или UI можно вынести в `docs/`, но README обязан оставаться самодостаточным для стандартного Docker Compose-пути. Заполнить все команды и ссылки реальными значениями проекта; не оставлять TODO/placeholders.

- [ ] Назначение пользователя, изменение статуса выполнения и комментарии работают.
- [ ] Все правила доступа из раздела 4 покрыты тестами.
- [ ] JWT-аутентификация работает.
- [ ] Swagger UI, Redoc и OpenAPI schema доступны.
- [ ] Основные тесты проходят.
- [ ] Ruff проходит без ошибок (либо все оставшиеся исключения объяснены).

- [ ] Современный адаптивный UI доступен на корневом URL приложения и поддерживает системную/светлую/тёмную темы с запоминанием выбора.

## 12. Порядок выполнения

Реализовывать задачу небольшими проверяемыми этапами:

1. Осмотреть репозиторий, определить, пустой ли он, проверить существующие инструкции, файлы, git status и выбранные инструменты. Сохранить уже работающий код.
2. Кратко представить план реализации и найденные риски. Не спрашивать пользователя о решениях, уже определённых этой спецификацией.
3. Настроить проект и зависимости, конфигурацию окружения, модели, миграции и разделение `models` / `services` / `selectors` / `api`.
4. Реализовать аутентификацию, задачи, permissions и комментарии.
5. Добавить тесты, включая негативные сценарии доступа; запускать их по мере реализации.
6. Добавить OpenAPI/Swagger/Redoc, адаптивный веб-интерфейс с тремя режимами темы, Dockerfile, Docker Compose, идемпотентную команду загрузки демо-данных и подробный README согласно `spec/FRONTEND.md` и `spec/DOCUMENTATION.md`.
7. Запустить все тесты, линтер и проверки миграций; проверить `docker compose up --build` и сценарий E2E на демо-данных; исправить обнаруженные ошибки и повторить проверки.
8. Проверить `git diff`, удалить случайные временные/секретные файлы и предоставить краткий отчёт.

Не заявлять, что команда или проверка прошла, если она фактически не запускалась. При ошибках окружения указать точную команду и ошибку, а также отдельно сообщить, какие проверки удалось выполнить.
